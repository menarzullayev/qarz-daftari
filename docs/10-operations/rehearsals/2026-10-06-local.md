# Local rehearsal of replication, failover, and restore: 2026-10-06

This is the record of a rehearsal on one developer machine. It is not the production measurement of the recovery targets (NFR-004). Read the section "What this does NOT prove" before using any number from this page.

## Scope

Story S1.5, local part only. No server was ordered, paid for, or deployed to. The stack and scripts are in `deploy/rehearsal/`; how they work is described in `deploy/rehearsal/README.md`.

Rehearsed: asynchronous streaming replication and WAL archiving with pgBackRest (ADR-015), manual scripted failover (ADR-014), point-in-time restore (Runbook 3), and a single-node S3-compatible file store (ADR-020).

## Commands run

Each run started from nothing and ended with everything removed:

```bash
bash deploy/rehearsal/scripts/down.sh
bash deploy/rehearsal/scripts/up.sh
bash deploy/rehearsal/scripts/verify.sh
bash deploy/rehearsal/scripts/down.sh
```

Run 3 used `QD_WRITER_SECONDS=110 bash deploy/rehearsal/scripts/verify.sh` so that the primary was killed at a different point of the 60-second archiving cycle.

Run 4 ran the same three scripts from a Linux shell, to check that they do not depend on Git Bash:

```bash
docker run --rm --network host \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v "<repository>/deploy/rehearsal:/work" docker:29-cli \
  sh -c 'apk add --no-cache bash curl coreutils sed grep gawk; cd /work; bash scripts/up.sh; bash scripts/verify.sh; bash scripts/down.sh'
```

`verify.sh` calls `failover.sh` and `pitr.sh` itself. The full output of every run was saved to `deploy/rehearsal/.out/verify-<run>.log`; those logs are not committed.

How to read the numbers:

- **Replication delay** is the time between the timestamp a row received on the primary and the moment a session on the standby first saw it. That session polls every millisecond, so the resolution is about one millisecond. Both databases share one machine and one clock.
- **Point-in-time restore** is measured from the start of `pitr.sh` to the restored instance answering queries as a writable database. It includes closing and archiving the current WAL segment on the live primary, which the script forces instead of waiting for `archive_timeout`.
- **Kill to first accepted write** starts just before `docker kill` and ends when an insert on the promoted standby returned. About 15 of the 20 seconds are three probes of the dead primary. Each probe took about 4.3 seconds, measured separately, because Docker's name service is slow to answer for a container that no longer exists. That delay belongs to Docker, not to PostgreSQL.
- **Rows lost after failover** counts rows whose commit the writing client saw acknowledged and which are missing on the promoted standby. Zero at one row a second means the gap was under one second. It does not mean asynchronous replication cannot lose a row.
- **Rows lost with the archive alone** is the loss if the standby had been lost together with the primary. It matched the age of the newest archived segment in every run (20, 19, 54, 17 rows against 19.6, 18.4, 53.7, 17.2 seconds) and stayed under the 60-second `archive_timeout`.

### What happens without the fence

Observed once by hand, after an earlier run, by starting the old primary with `QD_IGNORE_FENCE=1`:

- The old primary started as a normal writable database on timeline 1 while the promoted standby was writing timeline 2.
- It accepted an insert. The row did not exist on the promoted standby. Two databases were accepting writes.
- It archived its WAL segment `000000010000000000000008` and pgBackRest accepted it (`archived_count` 1, `failed_count` 0). The shared archive then held a segment that diverges from the promoted standby's history.

So neither PostgreSQL nor pgBackRest stops a returning old primary. Only the tooling does: `failover.sh` refuses to promote while the primary answers, and the fence file keeps the old primary from starting. The fence file depends on a volume shared by both containers, which two real servers do not have.

## What did not work or had to change

- **MinIO could not be used.** `docker pull minio/minio:RELEASE.2025-04-22T22-12-26Z` failed with "pull access denied ... repository does not exist or may require 'docker login'", and the same tag on quay.io failed with 401. The rehearsal uses Garage instead. This is a rehearsal choice, not a decision about the production file store.
- **Ports 55432 to 55434 could not be bound** on this Windows machine: they fall in a range reserved by the system (55334 to 55433). The defaults are 55532, 55533, and 55534.
- **Two earlier runs during development are not in the table.** Run 20261006T165812Z failed one check, the restore of the whole archive, because the script passed an option pgBackRest does not allow for that kind of restore; the script was fixed. Run 20261006T170146Z passed every check but printed an empty timeline value because of a formatting error in `verify.sh`; fixed. The four runs in the table used the final scripts.
- **Native Linux was not tested.** Run 4 used a Linux shell and Linux command-line tools, but the same Docker Desktop engine on Windows.

## What this does NOT prove

- **It is not the production measurement for the 1-hour and 5-minute targets (NFR-004).** Those targets must be measured on the real servers, with data at production scale, as the Operations document requires. Production servers in Uzbekistan do not exist yet.
- **It is one machine, one disk, one network.** Primary, standby, backup repository, and file store share one CPU, one SSD, one kernel, and one clock. A replication delay of a few milliseconds here says nothing about the link between two providers.
- **Restore times do not scale.** The database held a few hundred rows. A restore of 10 seconds here can be many minutes or more on a real database.
- **The failover time covers the database only.** Starting the API and worker on the standby, repointing DNS and the Telegram webhook, and the time a person needs to notice and decide are not included. Rebuilding a standby afterwards (second half of Runbook 2) was not rehearsed.
- **Fencing is not solved for production.** The fence file is a local device. With two servers that share nothing, the failover runbook needs a real step that keeps the old primary from serving and from archiving.
- **A broken link was not rehearsed.** The script cannot tell a dead primary from an unreachable one. The design says there is no failover while the primary is healthy; a person has to establish that.
- **The backup setup differs from the design.** The repository is a shared local volume, not a repository on the standby reached over the private tunnel, and there is no third location. The passphrase is in a local file. Only one full backup was taken; the weekly and daily schedule, retention, and the weekly automated restore test were not rehearsed.
- **File replication was not rehearsed.** The file store is one node. Losing it loses the files.
- **Zero rows lost is not a guarantee.** With asynchronous replication a commit acknowledged just before a crash can be missing on the standby. The test wrote one row a second and cannot see gaps under a second.
- **Load was absent.** One row a second is not the design capacity. Replication delay and archive volume under real load were not measured.
